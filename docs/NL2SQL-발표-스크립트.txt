============================================================
데이터플랫폼 안에서 동작하는 NL2SQL 엔진의 설계를 말씀드리겠습니다.

먼저 전체 그림입니다. 왼쪽이 데이터플랫폼의 분석 시스템입니다. ETL로 데이터를 적재하면 Kafka 토픽에 들어가고, 토픽을 각 언어로 분석해 결과 테이블과 리니지를 만듭니다. 
가운데가 이 문서의 범위인 NL2SQL 엔진입니다. 세 단계로 움직입니다.
첫째, 사람이 메타정보를 구조화합니다. 테이블과 컬럼 정보를 적재하고, 계산이 필요한 컬럼과 UTC 시각을 표시하고, 자주 쓰는 계산은 지표로 등록합니다.
둘째, LLM이 판단합니다. 질문에 맞는 테이블과 지표를 고르고 조회 명세를 JSON으로 씁니다. 애매하면 되묻습니다.
셋째, 규칙 기반 컴파일러가 이름과 함수를 검증하고 DB별 SQL로 바꿉니다.
이렇게 만든 SQL로 오른쪽의 UI 분석 페이지를 구성하는 것이 목표입니다.

아래 특징 세가지 입니다.
첫번째는 등록되지 않은 테이블, 컬럼, 함수는 컴파일러가 막기 때문에 구조적 오류가 SQL에 들어가지 않습니다.
두번째로 벡터DB와 유사도 검색 없이 메타 DB의 설명을 LLM이 직접 보고 고르므로 시스템이 단순합니다.
세번째로 질문을 넣으면 SQL을 돌려주는 API라서 에이전트나 UI가 도구처럼 부를 수 있습니다.

============================================================
핵심 원칙은 제목 그대로입니다. LLM은 판단하고, SQL은 컴파일러가 만듭니다.

LLM에게 SQL을 직접 쓰게 하면 네 가지 문제가 생깁니다. 없는 테이블이나 컬럼 이름을 지어내고, 누적값을 그대로 합치는 것처럼 계산식이 질문마다 달라지고, 지표 후보가 많으면 고르기 어렵고, 틀렸을 때 어디서 틀렸는지 알기 어렵습니다.

그래서 엔진은 세 가지 축으로 만들었습니다.
첫째, 지표가 정답 기준입니다. 계산이 필요한 질문은 사람이 검증한 SQL을 지표로 등록하고, LLM은 지표를 고르고 조건만 바꿉니다. 맞는 지표가 없으면 '지표 등록이 필요합니다'로 끝냅니다.
둘째, 단계별로 좁힙니다. 테이블을 고를 때 지표가 필요한지도 함께 판단하고, 다음 단계에는 고른 테이블과 지표만 넘깁니다.
셋째, LLM은 SQL 대신 JSON 조회 명세만 쓰고, 컴파일러가 검증과 UTC 보정, DB별 문법을 처리합니다.

모든 단계의 후보, 선택, 이유, 토큰은 질문 이력에 남습니다. 현재 범위는 SQL 생성까지이고, 실행 결과 조회는 다음 단계입니다.

============================================================
질문 하나가 SQL이 되는 다섯 단계입니다.

1단계 메타 조회는 LLM 없이 메타 DB에서 테이블, 컬럼, 지표를 읽습니다.
2단계에서 LLM이 테이블과 지표를 고르고, 지표가 필요한 질문인지 판단합니다.
3단계 분기는 규칙입니다. 애매하면 되묻고, 지표가 필요한데 없으면 등록 안내로 끝내고, 그 밖에는 다음으로 진행합니다.
4단계에서 LLM이 조회 명세, 즉 JSON AST를 씁니다. 지표를 쓰면 계산은 그대로 두고 기간, 조건, 묶음만 바꿉니다.
5단계에서 컴파일러가 검증하고 SQL로 바꿉니다. 실패하면 오류 메시지를 4단계로 돌려보내 다시 쓰게 합니다.

질문마다 SQL과 근거, 단계별 기록, 사용자 평가가 남고, 맞다고 평가한 질문은 평가셋으로 내보낼 수 있습니다.

============================================================
흔히 쓰는 RAG 방식, 즉 한 번 검색해서 SQL을 생성하는 방식과 비교해 보겠습니다.

후보를 찾을 때 RAG는 질문과 비슷한 것을 유사도로 찾지만, 이 엔진은 테이블 목록과 지표 설명을 LLM이 보고 고릅니다.
계산식은 RAG에서는 질문마다 달라질 수 있지만, 여기서는 등록된 지표의 계산식을 그대로 씁니다.
없는 이름은 RAG에서는 실행해 봐야 알지만, 여기서는 컴파일 단계에서 막고 다시 시킵니다.
애매한 질문에는 되묻고, 틀렸을 때는 단계별 기록으로 바로 원인을 찾습니다.

아래는 운영자가 미리 준비하는 다섯 가지입니다. 시스템 등록, 스키마 동기화, 테이블과 컬럼 설정, 관계 확인, 지표 등록입니다. 자세한 구조는 1장부터 3장에서 다룹니다.

============================================================
[슬라이드 5  구축과 운영]
실제로 구축할 때 누가 무엇을 하는지입니다. 한 줄로 말하면, 개발자가 한 번 구축하면 운영자는 질문만으로 데이터 분석을 할 수 있습니다.

개발자는 세 가지를 합니다.
첫째, 엔진 구축입니다. 메타 DB를 구성하고 LLM 서버를 연결하고 백엔드와 UI를 배포합니다.
둘째, 시스템 초기 설정입니다. 읽기 전용 계정으로 DB를 연결하고 동기화한 뒤, 원천 데이터의 코드값, 누적값, UTC 시각을 분석해 메타를 설정합니다. 바로네스 14개 테이블 기준으로 10분 정도 걸렸습니다.
셋째, 지표 등록과 검증입니다. 자주 묻는 계산을 SQL로 등록하고, 대표 질문과 변형 질문으로 테스트하면서 메타와 지표를 보완합니다. 이때 하루정도의 시간이 소요됩니다.

운영자는 평소에는 질문하고 생성된 SQL로 분석 페이지를 구성합니다. 가끔 '지표 등록이 필요합니다'가 나오면 지표를 등록하고, 신규 테이블이 생기면 재동기화만 하면 됩니다.

============================================================
[슬라이드 6  1장 메타 DB 테이블 정의서 1/4]
여기서부터 1장, 메타 DB 테이블 정의서입니다. 상세 컬럼은 자료로 보시고, 역할 위주로 말씀드리겠습니다.

meta_system은 조회 대상 DB입니다. 질문할 때 먼저 고르는 단위이고, 접속 정보와 업무 영역 설명을 가집니다. 업무 영역 설명은 LLM 프롬프트에 들어갑니다. 비밀번호는 AES-256-GCM으로 암호화하고 API 응답에서는 빼 둡니다.

meta_table은 테이블입니다. 동기화할 때 이름 기준으로 병합해서 ID가 유지되고, 사람이 쓰는 업무활용 설명이 LLM에 전달됩니다. DB에서 사라진 테이블은 지우지 않고 삭제 표시만 합니다.

============================================================
[슬라이드 7  1장 2/4, 약 1분]
meta_column은 컬럼 정보입니다. 1번부터 9번은 동기화가 채우고, 10번과 11번은 사람이 설정합니다.
UTC 시차는 UTC로 저장된 시각을 현지 시각으로 바꾸는 값이고, 계산 필요는 누적값처럼 그대로 합치면 틀리는 컬럼 표시입니다. 이 두 칸이 이 설계의 핵심입니다.

meta_relation은 테이블 조인 조건입니다. FK는 동기화할 때 자동으로 들어오고, FK가 없는 관계는 사용자가 직접 등록합니다.

============================================================
[슬라이드 8  1장 3/4, 약 1분]
metric은 지표입니다. 사용자가 SQL로 등록하면 AST로 바꿔 함께 저장합니다. 지표 설명과 같은 말은 테이블을 고를 때 LLM에 전달됩니다.
동기화 뒤 테이블이나 컬럼이 바뀌어 컴파일이 안 되면 상태가 broken으로 바뀌고 이유가 남습니다. 수정할 때마다 버전이 올라갑니다.

metric_table은 지표가 쓰는 테이블입니다. 지표 하나가 기본 테이블과 조인 테이블 여러 개를 쓸 수 있어 따로 둡니다.

============================================================
[슬라이드 9  1장 4/4, 약 1분]
ask_log는 질문 기록입니다. 질문, 고른 테이블과 지표, AST, SQL, 실패 사유, 되묻기, 시간과 토큰, 사용자 평가가 남습니다.

ask_trace는 단계별 LLM 기록입니다. 단계마다 무엇을 후보로 보냈고 무엇을 왜 골랐는지, 토큰과 시간이 남습니다. 결과가 틀렸을 때 어느 단계에서 틀렸는지 찾는 튜닝용 기록입니다.

이력 테이블 두 개는 생략했고, 원본은 schema.sql에 있습니다.

============================================================
[슬라이드 10  2장 메타정보 구조화 설계]
2장은 메타정보를 어떻게 구조화했는지입니다. 네 가지로 나뉩니다.
테이블 메타는 물리명, 원천 코멘트, 사람이 쓰는 업무활용 설명입니다.
컬럼 메타는 물리명, 타입, 코멘트이고 동기화가 채웁니다.
컬럼 설정은 사람이 하는 일로, 계산 필요와 UTC 시차를 표시합니다.
마지막으로 SQL 지표 등록입니다.

아래 표는 각 설계의 목적입니다. 질문자의 말과 DB 코멘트의 말이 달라서 업무 설명을 붙입니다. 물리명만으로는 뜻을 알 수 없어 코드값과 단위가 코멘트에 있어야 합니다. 누적값을 합치면 틀린 답이 되는데 컴파일러는 이걸 판단할 수 없어서, LLM이 계산 필요 표시를 보고 지표가 필요한지 판단합니다. UTC 시차는 컴파일러가 자동 보정하고, 계산식은 사람이 검증한 SQL을 지표로 등록합니다.

============================================================
[슬라이드 11  3장 구조화 결과]
3장은 실제 바로네스의 bms_log 테이블에 적용한 결과입니다.

왼쪽이 원천 카탈로그 그대로이고, 오른쪽이 동기화와 사람 설정을 거친 결과입니다. 61개 컬럼 중 사람이 손댄 것은 계산 필요 7개와 UTC 보정 1개뿐입니다. 나머지는 코멘트를 그대로 전달합니다.

이렇게 설정하면 테이블 선택 프롬프트에 'uman_time 무인 가동 시간, 계산 필요' 형태로 들어가고, 누적 컬럼으로 지표 다섯 개를 등록했습니다.

============================================================
[슬라이드 12  4장 메타정보 활용 1/2]
4장은 메타정보가 실제 질문에서 어떻게 쓰이는지입니다. 예시 질문은 '최근 5일 차량별 무인 가동시간 합계'입니다.

질문의 '최근 5일'은 UTC 보정된 collect_datetime, '차량별'은 vehicle_id, '무인 가동시간 합계'는 계산 필요인 uman_time에 대응합니다. 그래서 '무인 가동시간' 지표를 씁니다. 지표는 차량별, 일별로 하루의 최댓값에서 최솟값을 뺀 값입니다.

LLM 요청은 두 번입니다. 첫 번째에서 테이블과 지표를 고르고, 두 번째에서 지표 AST를 바탕으로 기간만 최근 5일로 바꿉니다. 컴파일러는 이를 하위 쿼리로 두고 바깥에서 차량별로 합칩니다.
맞는 지표가 없는 질문, 예를 들어 무인 절단 시간은 첫 단계에서 '지표 등록이 필요합니다'로 끝납니다.

============================================================
[슬라이드 13  4장 2/2, 약 1분]
LLM 연동 인터페이스 요약입니다.
테이블 선택 인터페이스는 테이블 목록과 지표 설명을 보내고, 테이블, 지표 필요 여부, 지표, 이유, 되묻기를 JSON으로 받습니다.
AST 생성 인터페이스는 고른 테이블의 컬럼과 지표 SQL, AST를 보내고, AST를 받습니다. 컴파일에 실패하면 고칠 점을 붙여 다시 요청합니다.


============================================================
[슬라이드 14  5장 질문이 SQL이 되는 흐름, 약 2분]
앞의 내용을 실제 실행 기록 한 장으로 정리했습니다. 같은 질문, '최근 5일 차량별 무인 가동시간 합계'입니다.

메타 DB 조회는 LLM 없이 0.04초입니다.
테이블 선택에 4.9초가 걸렸고, bms_log와 '무인 가동시간' 지표를 골랐습니다. 지표가 있으니 진행합니다.
AST 생성에 34.4초가 걸렸고, 첫 시도에 컴파일이 성공했습니다. '최근 5일'은 10월 12일부터 16일로, '차량별 합계'는 바깥 SUM으로 바뀌었습니다.
마지막으로 질문과 단계별 기록이 저장됩니다.

아래 SQL의 색을 보시면, 파란 부분은 지표 정의, 주황 부분은 LLM이 판단한 조건, 회색 부분은 컴파일러가 자동으로 붙인 UTC 보정과 문법입니다. LLM이 직접 쓴 부분은 조건뿐이라는 점이 핵심입니다.

============================================================
[슬라이드 15  6장 LLM 결과 파싱 및 쿼리 전송, 약 1분 30초]
6장은 LLM 응답을 어떻게 읽고, 앞으로 쿼리를 어떻게 보낼지입니다.

파싱은 코드펜스를 지우고 JSON을 꺼낸 뒤 테이블과 지표 이름을 실제 목록과 대조합니다. 틀리면 이유를 붙여 다시 묻습니다. AST는 컴파일러가 테이블과 컬럼, 함수, 집계 규칙을 검사하고 UTC 보정 후 SQL로 조합합니다.

쿼리 전송과 DB 조회는 TO-BE 설계입니다. SELECT 한 문장만 허용하고, 읽기 전용 트랜잭션으로, 행 수와 시간을 제한해 실행합니다. 접속 정보는 메타 동기화와 같은 드라이버를 쓰고, 비밀번호는 메모리에서만 복호화합니다.
지금은 지표 등록 때 원본과 변환 SQL을 읽기 전용으로 실행해 비교하는 데까지 구현돼 있습니다.

============================================================
[슬라이드 16  7장 변형 질문 테스트, 같은 뜻 다른 표현, 약 2분]
